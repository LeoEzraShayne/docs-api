# Requirements Definition Sheet Level Rules

The Requirements Document is a business-level document.

Do NOT generate implementation-level content.

Do NOT generate detailed technical design.

The purpose is to define WHAT the system needs.

Not HOW the system will be implemented.

---

API Sheet Rules

The API sheet is only for requirement definition.

Columns:

- API Name
- Purpose
- Caller
- Callee
- Business Description

Examples:

Create Order API

Purpose:
Create customer order

Caller:
Web Frontend

Callee:
Backend System

Business Description:
Create a new order and return order number

Do NOT generate:

- URL
- Request JSON
- Response JSON
- Error Codes
- Database Logic

These belong to Basic Design or Detailed Design.

---

Screen Sheet Rules

Only define:

- Screen ID
- Screen Name
- Purpose
- Main Functions

Do NOT generate:

- Layout Design
- Component Design
- Field Validation Rules

---

Database Sheet Rules

Only define:

- Entity Name
- Purpose
- Main Data Items

Do NOT generate:

- Data Types
- Length
- PK/FK Design
- Index Design

---

Permission Sheet Rules

Only define:

- Role Name
- Accessible Functions

Do NOT generate detailed permission matrix.

---

Business Flow Sheet Rules

Generate business-level flow.

Do NOT generate system sequence diagrams.

---

Non Functional Requirement Sheet Rules

Generate:

- Security
- Performance
- Availability
- Audit
- Backup

at requirement level only.

Do NOT generate implementation details.
# Document Dependency Rules

Requirements Document is the first document in the generation chain.

It does NOT support upstream document selection.

Input source is always:

Project Information
+
Requirements Input Form

The generated Requirements Document may later be used as an upstream source for:

- Basic Design
- Detailed Design
- Unit Test Specification
- Integration Test Specification

Requirements Document is the root document of the document generation workflow.
